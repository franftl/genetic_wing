# UAV FP — Research Note 9: Open-Source Python Implementations, Geometry Parametrization, and Whether You Need CAD

*Compiled 13 August 2026. Follow-up to Research Note 8 (AI-optimized flying wing design).*

## Short answers

Yes, open-source Python code for exactly this exists — and one library in particular (AeroSandbox, paired with its sister project NeuralFoil) is close to being "the paper, but as a maintained library you can pip install." Wing geometry is parametrized the normal way aircraft designers always have (span, chord/taper, sweep, twist, airfoil shape), just expressed as variables in code instead of a spreadsheet. And no — VLM does not need a 3D solid body at all; that's a fundamentally different kind of input than what CFD needs, which is the key thing to understand before you touch any CAD tool. Fusion 360 has a role, but later, for structure and manufacturing, not for the aerodynamic optimization loop itself.

## 1. Open-source Python code that does this

**AeroSandbox** (`peterdsharpe/AeroSandbox` on GitHub, installable via `pip install aerosandbox`) is the standout answer. It's a pure-Python aircraft design framework built specifically for design optimization: you define geometry (wings, fuselages, whole aircraft) directly in code, run aerodynamic analysis including a built-in Vortex Lattice Method solver, and optimize using automatic differentiation for gradient-based optimization — the author's own framing is that "design problems with tens of thousands of decision variables solve in seconds on a laptop." It ships with actual runnable tutorial notebooks in the repo, including one titled exactly ["01 - Vortex Lattice Method.ipynb"](https://github.com/peterdsharpe/AeroSandbox/blob/master/tutorial/06%20-%20Aerodynamics/01%20-%20AeroSandbox%203D%20Aerodynamics%20Tools/01%20-%20Vortex%20Lattice%20Method/01%20-%20Vortex%20Lattice%20Method.ipynb) that walks through setting up and running a VLM analysis in Python step by step — genuinely the fastest way to see the whole pipeline concretely rather than reading about it abstractly.

Even more directly relevant: the same author built **NeuralFoil** (`peterdsharpe/NeuralFoil`, also pip-installable), a pretrained neural network that predicts 2D airfoil aerodynamic performance (lift, drag, moment) directly from airfoil shape — pure Python/NumPy, physics-informed, published with its own paper. This is essentially an already-trained version of the ANN "surrogate model" concept from the Tran et al. paper you found — you don't have to train your own neural network from scratch to get a fast aerodynamics approximator; NeuralFoil already exists, is maintained, and plugs directly into AeroSandbox's optimization tools (there's a tutorial notebook specifically titled ["02 - NeuralFoil Optimization.ipynb"](https://github.com/peterdsharpe/AeroSandbox/blob/master/tutorial/06%20-%20Aerodynamics/02%20-%20AeroSandbox%202D%20Aerodynamics%20Tools/02%20-%20NeuralFoil%20Optimization.ipynb)). Worth noting one real design choice here: AeroSandbox/NeuralFoil favor gradient-based optimization via automatic differentiation rather than genetic algorithms. That's arguably a more modern and computationally efficient approach than the GA method in the paper you found — gradient-based methods converge faster when they're available — but a genetic algorithm is easier to understand and explain, doesn't require differentiable code, and is what the published literature you're citing actually used. Worth deciding deliberately which you want to implement (or note in your thesis that you evaluated both).

If you'd rather use a long-established, extensively validated VLM engine instead of AeroSandbox's own solver, **AVL** (Athena Vortex Lattice, from MIT — the same tool referenced throughout the aircraft design literature for decades) has several Python wrapper projects that let you script it the same way: [`OptVL`](https://github.com/joanibal/OptVL) specifically adds automatic differentiation and gradient-based optimization on top of AVL, while [`AVLWrapper`](https://github.com/jbussemaker/AVLWrapper) and [`avlpy`](https://github.com/coursekevin/avlpy) offer more general-purpose Python scripting interfaces for running multiple AVL sessions programmatically. For coupling aerodynamics with structural sizing (relevant once you're also optimizing the internal spar/rib structure, per Note 8), **OpenAeroStruct** (`mdolab/OpenAeroStruct`) is a Python VLM + structural finite-element tool built on NASA's OpenMDAO framework, specifically designed for coupled aerostructural optimization — the natural next step if the pure-aerodynamic optimization goes well and you want to extend into structure.

For the genetic algorithm piece specifically, if you decide to replicate the paper's GA approach rather than AeroSandbox's gradient-based approach: **PyGAD** and **DEAP** are the two standard, well-documented, general-purpose Python genetic algorithm libraries, neither aerospace-specific but both commonly used to wrap around an aerodynamics solver — you write a function that takes a candidate design and returns a fitness score (e.g., predicted glide ratio from your surrogate), and the library handles the population/selection/mutation loop around it.

## 2. Parametrizing the flying wing design

This part isn't a machine-learning problem — it's standard aircraft conceptual design, just expressed as variables instead of drawn by hand. A flying wing is typically parametrized by a small, well-understood set of numbers: wingspan, root and tip chord (or equivalently, a taper ratio), sweep angle, the twist/washout distribution along the span (critical for a flying wing specifically, since it substitutes for a tail in providing pitch stability), the airfoil section(s) used along the span (flying wings typically use reflexed airfoils — Eppler or MH-series — precisely because they generate a stabilizing pitching moment that a tailless aircraft needs), and dihedral. Each of these becomes a design variable your optimizer varies. This is exactly the parametrization scheme both the AeroEd student project and the Tran et al. paper use, and it's exactly what AeroSandbox's or AVL's geometry definitions expect as input — there's no translation step needed between "how aircraft designers think about wing shape" and "what the code wants."

## 3. Does VLM need a 3D solid body? No — and this is the key conceptual point

This is worth being precise about, because it's genuinely different from how CFD works and from how CAD modeling works, and mixing the two up leads to a lot of wasted effort. The Vortex Lattice Method doesn't analyze a solid object at all — it represents the wing as a thin, zero-thickness **mean camber surface** (essentially the curved sheet that the airfoil's camber line sweeps out along the span), discretized into a grid of flat panels, each carrying a horseshoe vortex. The method solves for the vortex strengths that satisfy the flow boundary condition, and from that derives lift, induced drag, and stability derivatives. What this means practically: your geometry input is just airfoil coordinates (a 2D curve, typically 50-200 x/y points) plus the planform parameters from section 2 — not a solid, not a volume mesh, not something you'd build in a CAD modeler. This is also why VLM runs so fast (panel counts in the hundreds, not the millions of cells a CFD volume mesh needs) — it's solving a much simpler mathematical problem by design, at the cost of not capturing things like flow separation or thickness effects in detail (acceptable for conceptual-design-stage optimization, which is exactly your use case here).

## 4. So where does CAD (Fusion 360 or otherwise) actually fit in?

Not in the optimization loop itself — that part is fully scriptable in Python, as described above, whether you use AeroSandbox's own geometry classes or OpenVSP's Python API (OpenVSP also has an official, documented Python interface for building parametric 3D geometry entirely in code, without opening its GUI). CAD becomes relevant at the next stage, once you have a winning design and need to turn it into something manufacturable: adding actual structure (spars, ribs, skin) with real thickness and material, and preparing files for whatever manufacturing method you land on from Note 8. If you go the CNC hot-wire foam cutting route, you often don't need full solid CAD at all — the cutter just needs the airfoil coordinates and planform geometry directly (which your optimization already produced), fed through the cutter's own path-planning software. Fusion 360 becomes genuinely useful if you want to design and 3D-print structural components (ribs, spar mounts, control horn brackets) or if you want a proper solid model for documentation, stress analysis, or a more complex composite build — but that's a downstream CAD/manufacturing step, separate from and after the Python-based aerodynamic optimization loop, not a prerequisite for it.

## Suggested practical path

Given everything above, a reasonable implementation order: install AeroSandbox and work through its VLM tutorial notebook to get a baseline flying-wing analysis running end to end; parametrize your design variables (span, taper, sweep, twist distribution, airfoil) as AeroSandbox geometry objects; decide between AeroSandbox's built-in gradient-based optimizer (faster to set up, since it's already integrated) or wrapping the analysis in PyGAD/DEAP for a genetic-algorithm approach closer to the published paper; and only bring in Fusion 360 (or OpenVSP for a more automated path) once you're translating a finalized optimized geometry into a physical, manufacturable part.
